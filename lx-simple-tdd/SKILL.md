# 简单TDD流程

## 1. Think Before Coding

- 将任务拆分后呈现给用户
- 每个任务直接给出方案，呈现用户后，询问是否遵循TDD（是/否）
- 选择TDD后，强制执行红绿测试用例的编写和验证流程
- 选择非TDD后，直接实现任务逻辑，不编写测试用例
- **强制**：红色用例不允许编译失败，遇到未定义方法/属性先定义再回来继续


## 1.1 强制交互节点（必须使用 AskUserQuestion）

| 节点 | 时机 | 选项 |
|------|------|------|
| 1 | 任务拆分后 | 是否TDD |
| 2 | 每一个任务编写前后 | 必须有红绿测试用例 |
| 3 | 红绿测试用例编写中 | 必须是单元测试，不能是集成测试 |

**禁止**：不执行红色用例编写，直接实现任务逻辑；不执行绿色用例编写，直接实现下一个任务；
**必须**: 不管当前项目风格如何，都只能编写单元测试，不能编写集成测试用例;


## 1.2 流程

需求 → 任务拆分 → 方案呈现 → 判断是否采用TDD
- 是
    1. 编写红色用例 → 运行失败
    2. 实现任务逻辑 
    3. 编写绿色测试用例，用例通过
    3. 循环：下一个任务-> 回到步骤1，编写红色用例
    4. 全部任务完成
- 否
    1. 直接实现任务
    2. 循环：处理下一个任务
    3. 全部任务完成

## 2. Simplicity First

**用最少代码解决问题，不做多余设计**

- 不加未要求的功能
- 不为单次使用做抽象
- 不加未要求的灵活性/可配置性
- 不为不可能场景做错误处理
- 200行能50行解决就重写

## 3. Surgical Changes

**只动必须动的，只清理自己制造的垃圾**

编辑现有代码时：
- 不"改进"相邻代码、注释或格式
- 不重构未损坏的部分
- 匹配现有风格
- 发现无关死代码只提及不删除

变更产生孤立代码时：
- 删除自己造成的未使用导入/变量/函数
- 不删除原有死代码

## 4. Goal-Driven Execution

**定义成功标准，循环直到验证通过**

将任务转为可验证目标：
- "添加验证"→"写无效输入测试，然后通过"
- "修复bug"→"写复现测试，然后通过"
- "重构X"→"确保重构前后测试通过"
