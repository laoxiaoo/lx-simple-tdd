# 规则

## 1. Think Before Coding

- 将任务拆分后呈现给用户
- 每个任务直接给出方案，呈现用户，询问是否遵循TDD（是/否）
- 是：先写红色测试→运行→确认→写代码→运行绿色→执行下一个任务
- 否：确认后实现
- **强制**：红色用例不允许编译失败，遇到未定义方法/属性先定义再回来继续
- 单测结束后咨询是否进行集成测试


## 1.1 强制交互节点（必须使用 AskUserQuestion）

| 节点 | 时机 | 选项 |
|------|------|------|
| 1 | 任务拆分后 | 是否TDD |
| 2 | 红色测试运行后 | 确认/自定义 |
| 3 | 绿色测试运行后 | 下一步/修改 |
| 4 | 每个任务完成后 | 满意/调整 |
| 5 | 全部单测完成后 | 是否集成测试 |

**禁止**：跳过任何交互节点；未确认就修改代码；连续执行多任务不确认

## 1.2 TDD 流程

需求→[节点1]任务拆分→是否TDD？→是→红色测试→[节点2]确认→实现→绿色测试→[节点3]下一步→[节点4]满意？→循环→[节点5]集成测试？

## 2. Simplicity First

**用最少代码解决问题，不做多余设计**

- 不加未要求的功能
- 不为单次使用做抽象
- 不加未要求的灵活性/可配置性
- 不为不可能场景做错误处理
- 200行能50行解决就重写

## 3. Surgical Changes

**只动必须动的，只清理自己制造的垃圾**

编辑现有代码时：
- 不"改进"相邻代码、注释或格式
- 不重构未损坏的部分
- 匹配现有风格
- 发现无关死代码只提及不删除

变更产生孤立代码时：
- 删除自己造成的未使用导入/变量/函数
- 不删除原有死代码

## 4. Goal-Driven Execution

**定义成功标准，循环直到验证通过**

将任务转为可验证目标：
- "添加验证"→"写无效输入测试，然后通过"
- "修复bug"→"写复现测试，然后通过"
- "重构X"→"确保重构前后测试通过"
