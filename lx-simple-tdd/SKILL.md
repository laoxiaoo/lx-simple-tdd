# 简单TDD流程

## 1. Think Before Coding

- **主 Agent 职责**: 需求分析、任务拆分、方案呈现、流程协调
- 每个任务直接给出方案，呈现用户后，询问是否遵循TDD（是/否）
- 选择TDD后，强制执行多子代理协作的红绿测试流程
- 选择非TDD后，直接实现任务逻辑，不编写测试用例
- **强制**：红色用例不允许编译失败，遇到未定义方法/属性先定义再回来继续


## 1.1 强制交互节点（必须使用 AskUserQuestion）

| 节点 | 时机 | 选项 |
|------|------|------|
| 1 | 任务拆分后 | 是否TDD |
| 1.5 | 选择TDD后 | 为 tdd-coder 和 tdd-reviewer 分别指定模型 |
| 2 | 每一个任务编写前后 | 必须有红绿测试用例 |
| 3 | 红绿测试用例编写中 | 必须是单元测试，不能是集成测试 |
| 4 | Code Review后 | Review是否通过，是否需要补充测试 |

**禁止**：不执行红色用例编写，直接实现任务逻辑；不执行绿色用例编写，直接实现下一个任务；
**必须**: 不管当前项目风格如何，都只能编写单元测试，不能编写集成测试用例;


### 子 Agent 定义

本技能使用两个固定的用户级子 Agent，定义文件位于 `~/.qoder/agents/`：

| Agent 名称 | 角色 | 职责 |
|------------|------|------|
| `tdd-coder` | 编码代理 | 编写红色测试用例、补充测试用例、实现业务逻辑 |
| `tdd-reviewer` | 审查代理 | Code Review 红色用例的编译正确性和覆盖度 |

### 模型指定

在TDD流程开始前，使用 AskUserQuestion 询问用户为两个子Agent分别指定模型：

- **tdd-coder 模型**: 默认 `Qwen3.7-Max`，用户可指定任意模型（如 `lite`、`efficient`、`performance`、`auto` 或具体模型名）
- **tdd-reviewer 模型**: 默认 `performance`，用户可指定任意模型（如 `lite`、`efficient`、`performance`、`auto` 或具体模型名）

调用子Agent时，通过 Agent 工具的 prompt 参数在开头附加模型切换指令：
```
[模型指令: 请使用 {model_name} 模型]

{实际任务prompt}
```

如果用户未指定模型，则使用各Agent的默认模型（tdd-coder: `Qwen3.7-Max`，tdd-reviewer: `performance`）。

### 流程

```
需求 → 主Agent任务拆分 → 方案呈现 → 判断是否采用TDD
├─ 是 (TDD)
│   → 询问用户为 tdd-coder 和 tdd-reviewer 指定模型
│   对每个任务循环执行：
│   Step 1: 主Agent调用 tdd-coder → 编写红色测试用例（预期失败）
│   Step 2: 主Agent调用 tdd-reviewer → Code Review红色用例
│           - 检查编译正确性（语法、类型、导入）
│           - 检查覆盖度（正常路径、异常路径、边界值）
│   Step 3: 主Agent根据Review结果决策
│           - 不通过 → 返回 tdd-coder 补充测试 → 回到Step 2
│           - 通过 → 继续Step 4
│   Step 4: 主Agent调用 tdd-coder → 实现业务逻辑
│   Step 5: 主Agent运行绿色测试用例 → 验证通过
│   Step 6: 下一个任务 → 回到Step 1
│   全部任务完成
│
└─ 否 (非TDD)
    1. 直接实现任务
    2. 循环：处理下一个任务
    3. 全部任务完成
```

### 调用 tdd-coder 的 Prompt 模板

**编写红色用例**:
```
任务: {task_name}
描述: {task_description}

请为该任务编写单元测试（红色用例）。
要求:
1. 测试用例必须能编译通过
2. 覆盖正常路径、异常路径、边界值
3. 只写测试用例，不实现业务逻辑
4. 测试预期结果应为失败（业务逻辑尚未实现）
5. 必须是单元测试，不能是集成测试
```

**补充测试用例**:
```
根据以下Review意见，补充测试用例：
{review_feedback}

请补充缺失的测试场景，确保覆盖所有边界条件。
```

**实现业务逻辑**:
```
任务: {task_name}
测试用例已通过Review，请实现业务逻辑使测试通过。
要求:
1. 只实现必要的逻辑，不做多余设计
2. 保持代码简洁，遵循现有代码风格
```

### 调用 tdd-reviewer 的 Prompt 模板

**Code Review 红色用例**:
```
请Review以下测试用例代码：
文件: {test_file_path}
任务: {task_name}

Review检查项:
1. 编译正确性
   - 语法是否正确
   - 类型是否匹配
   - 导入是否完整
2. 测试覆盖度
   - 是否覆盖正常路径
   - 是否覆盖异常路径
   - 是否覆盖边界值
   - 是否有遗漏的场景
3. 测试质量
   - 测试命名是否清晰
   - 断言是否合理

输出格式:
- 通过项: [列出]
- 问题项: [列出具体问题]
- 建议: [列出改进建议]
- 结论: 通过/不通过
```

## 2. Simplicity First

**用最少代码解决问题，不做多余设计**

- 不加未要求的功能
- 不为单次使用做抽象
- 不加未要求的灵活性/可配置性
- 不为不可能场景做错误处理
- 200行能50行解决就重写

## 3. Surgical Changes

**只动必须动的，只清理自己制造的垃圾**

编辑现有代码时：
- 不"改进"相邻代码、注释或格式
- 不重构未损坏的部分
- 匹配现有风格
- 发现无关死代码只提及不删除

变更产生孤立代码时：
- 删除自己造成的未使用导入/变量/函数
- 不删除原有死代码

## 4. Goal-Driven Execution

**定义成功标准，循环直到验证通过**

将任务转为可验证目标：
- "添加验证"→"写无效输入测试，然后通过"
- "修复bug"→"写复现测试，然后通过"
- "重构X"→"确保重构前后测试通过"
